# Dashboards vs Microsoft Fabric: Finance and the chart of accounts

Data validation run on **2026-10-21**, comparing what the dashboards show (live Orion, through the app's
own query functions) with MBAL's data in Microsoft Fabric (lakehouse `lh_enterprise_core`, its
notebooks and seed map, and the Power BI semantic models and reports on top). **This is a report only:
no dashboard code, query, data file, test or config was changed, and nothing in Fabric was created,
edited, scheduled or run.**

This file holds statuses, % differences, counts and account codes/names only. The full report with
real figures is local to the manager's PC (`Documents/MBAL-BI-reports/fabric-validation-2026-10-21.html`).
Every hand query is in [`queries.sql`](queries.sql) and [`queries.dax`](queries.dax), and every
company × month × measure result is in [`finance-comparison.csv`](finance-comparison.csv).

## Verdict

- **Yes for the ledger itself.** The posted GL behind the Finance dashboard matches the GL Fabric loaded from Orion. The September 2026 trial balance agrees on all 478 company × account rows (debit, credit and net, to the fils), and all 6,199 company × month × account net totals from Oct 2025 to today agree, October included. Nothing is lost or doubled between Orion, our dashboard and the lakehouse.
- **No for the P&L lines, until Finance settles one chart of accounts.** Revenue, cost of sales, G&A and net profit differ from Fabric because the two sides classify accounts differently. Ours is data/chart-of-accounts.csv: 446 accounts, generated by code range and name (the project README asks Finance to review it). Fabric uses a 105-account P&L map (Files/Finance/map/main_acount_map_new). The two disagree on the P&L line of 24 shared codes. Fabric also has a fourth line, "Provisions" (depreciation, interest, provisions, charity, tax), which we fold into G&A. And Fabric's INNER JOIN drops 32 P&L codes that are not in its map, 6 of which have postings this year.
- **Size of it (current YTD, all companies).** G&A differs by 25.75% (mostly Provisions), cost of sales by 0.95%, revenue by 0.43%, gross profit by 2.15% and net profit by 0.14%. Net moves only through the accounts Fabric drops, because a move between P&L lines leaves net unchanged.
- **Fabric's own PNL report adds more.** It does not filter posted lines, so unposted (CYU) journals count. It also applies ABS() to each P&L line, so a line that nets the "wrong" way shows with the wrong sign (13 company-month lines since Oct 2025). Our dashboard uses posted lines only and keeps signs.
- **Other dashboards.** AR (outstanding, >90 days), AP (owed, >90 days, prepaid), pending POs and open sales orders match Fabric exactly. Sales match for September. YTD differs only by October invoices Fabric holds that are still UNCONFIRMED; the confirmed-only figure matches to the fils. Current stock value differs by 0.84%, because Fabric values stock from the procurement summary (qty × WAC). The September month-end stock value matches.

### Recommendations (nothing was changed)

1. **Finance owns one chart of accounts.** Use Fabric's 105-row map (`Files/Finance/map/main_acount_map_new`)
   as the base for P&L lines: it is the Finance-curated seed, and ours was generated by code range. Then
   settle the open questions: is "Provisions" a separate P&L line (Fabric) or part of G&A (ours)? Which
   line do 40724, 40827, 40829, 40854, 40870 and 40877 belong to (cost of sales or G&A)? Where does
   40837, profit/loss on investments, go?
2. **Add the missing P&L codes to Fabric's map**, at least those with postings this year: 30801, 40727,
   40818, 40834, 40864 and 40872. Better still, change the "Data Ingestion" notebook's INNER JOIN to a
   LEFT JOIN with an "Unmapped" bucket, so a new GL code can never silently vanish from Fabric's P&L.
3. **Fabric "PNL - All" report:** filter posted lines (`TD_STATUS` ending `C`) and remove the `ABS()`
   in the line measures.
4. **Then update `data/chart-of-accounts.csv`** (a data file; no code change) to the agreed map, keeping
   our balance-sheet rows. The GL already matches, so the P&L lines will then match too.
5. **Fabric housekeeping:** the "Pending POs" report reads `pending_pos`, which has not loaded since
   2026-06-05 (its notebook step is commented out); the current-year sales extract keeps UNCONFIRMED
   invoices; three Direct Lake models show failed framing attempts (CEO View, Receivables & Payables,
   Inventory Model).

## 3. Finance figures

Same rules on both sides: posted lines only (`TD_STATUS` ending `C`), NVL on debit/credit, signed (revenue
positive, costs negative). Our side is the app's `financeMonthly` / `financeKpis`. Fabric's side is
`dbo.finance` summed by its own level_1, with net = Revenue + Cost of sales + G&A + Provisions (its "Net
Profit"). **MATCH** = |diff| ≤ 0.5% and ≤ AED 1,000; anything else is **DIFF**. Each DIFF is split per
account into a _mapping_ part (the account sits on another line, or is missing in Fabric) and a _load_
part (Fabric's GL ≠ Orion's for that account, company and month). **The load part is zero for every
DIFF**, so refresh lag, filters, sign, currency, irrelevant companies and missing rows are all ruled out
for the like-for-like comparison.

## 6. Method

- Fabric sign-in: Azure CLI session (DefaultAzureCredential) as the BI account; SQL through sqlcmd (Go) on lh_enterprise_core's SQL analytics endpoint; DAX through the Power BI REST executeQueries API (the FabricIQ MCP server did not connect); item and job metadata through the Fabric REST API (GET, and getDefinition for read-only inspection of the pipeline, notebook, model and report definitions).
- Workspaces: "Data Engine" (lh_enterprise_core, pipelines, notebooks) and "Dashboards" (Production_Lakehouse, whose finance/gl/… tables are OneLake shortcuts to lh_enterprise_core; Finance semantic model; PNL - All and other reports).
- Our side: the app's own functions from lib/server/queries/* in oracle mode, in a fresh process (cache empty), loaded through Vitest with the .env read by process.loadEnvFile(). The .env was never printed or copied. Per company: financeMonthly, accountBalances (YTD and September), financeKpis; all companies: financeKpis, financeMonthly, accountBalances; plus salesKpis, inventoryKpis, monthEndTrend, pendingKpis (2y and all), arSummary, apSplit, openBookKpis (2y and all).
- Two extra Orion hand queries (O3, O4) for active accounts and unposted lines; two more during root-cause tracing (sales by company/month/type, stock by company). All SELECT only.
- Fabric hand queries F0–F12 in queries.sql, DAX in queries.dax. The comparison and root-cause split ran in Python on the two result sets; thresholds MATCH = |diff| ≤ 0.5% and ≤ AED 1,000 (relative to our figure).
- Periods: last 12 closed months Oct 2025 – Sep 2026, current YTD 1 Jan – 21 Oct 2026, latest closed month Sep 2026. Companies: all 21 in Orion's company master; 17 have GL postings in the window. Fabric marks 90 and 460 as Irrelevant; neither has postings in the window, so it changes nothing.
- Nothing was changed in the app, Orion or Fabric. The only Fabric job in the window was the scheduled 13:00 run.

### Re-running the check

1. Fabric: `az login` with an account that can read the "Data Engine" workspace, look up the
   lh_enterprise_core SQL endpoint (`GET /v1/workspaces/<workspace-id>/lakehouses/<lakehouse-id>`,
   `properties.sqlEndpointProperties.connectionString`), replace the placeholders in `queries.sql` and run
   Part A with `sqlcmd -d lh_enterprise_core --authentication-method ActiveDirectoryDefault`. Run
   `queries.dax` against the Finance semantic model (Dashboards workspace) through the executeQueries API.
2. Orion: run Part B with the app's read-only credentials, or call the functions listed above in oracle
   mode with the cache empty.
3. Compare at the grain of each query: company × month × account (F3/F4 vs O1), company × account (F5 vs
   O2), account (F2 vs O3).

Spot checks for QA (same results on both sides): **F1** gives the 105 Fabric map rows used in section 2;
**F5 vs O2** for any company gives identical debit/credit/net per account for September 2026; **F4 vs
O1** for any company and closed month gives identical net per account.
